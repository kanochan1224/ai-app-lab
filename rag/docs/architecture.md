# 架构与关键设计决策

面向面试的说明文档：这份文件解释「为什么这样设计」，而不是「代码怎么写」。

## 一、整体链路

```
                    data/raw/*.md|txt|pdf|docx
                              │
                    ┌─────────▼─────────┐
                    │ 1. 解析 loader    │  多格式归一成「带层级标题的纯文本」
                    └─────────┬─────────┘
                              │  LoadedDocument(title, text, metadata)
                    ┌─────────▼─────────┐
                    │ 2. 切分 chunker   │  fixed / recursive / semantic 三选一
                    └─────────┬─────────┘
                              │  Chunk(chunk_id, text, section_path, lines)
              ┌───────────────┴────────────────┐
              │                                │
    ┌─────────▼─────────┐            ┌─────────▼─────────┐
    │ 3a. 向量化 + Chroma│            │ 3b. BM25 稀疏索引 │
    │   (稠密，语义近似)  │            │  (稀疏，词项精确)  │
    └─────────┬─────────┘            └─────────┬─────────┘
              │  top 20                        │  top 20
              └───────────────┬────────────────┘
                    ┌─────────▼─────────┐
                    │ 4. RRF 加权融合    │  只用名次，免疫量纲差异
                    └─────────┬─────────┘
                              │  融合候选池 20
                    ┌─────────▼─────────┐
                    │ 5. cross-encoder  │  精排 top 5
                    └─────────┬─────────┘
                              │
                    ┌─────────▼─────────┐
                    │ 6. 带引用生成      │  证据不足则拒答
                    └─────────┬─────────┘
                              │
                    答案 + [n] 引用 + 召回片段 + 链路耗时
```

## 二、关键设计决策与理由

### 1. 为什么在纯向量检索之外加 BM25？

向量模型擅长语义相似，但对「专有名词、缩写、公式符号、数字」不敏感。
课程场景里学生大量提问是术语级的：「C4.5 和 ID3 的区别」「K 折交叉验证 K 取多少」
「gamma 和 C 的区别」。这类查询里关键词本身携带绝大部分信息量，
BM25 的精确词项匹配反而更可靠。

**证据**：评估报告里的消融实验表（`data/eval/reports/*.md`）显示
「仅 BM25」在部分术语型问题上优于「仅向量」，而两者融合后的 Hit@5 / MRR 最高。
这正是混合检索存在的理由，也是能在面试里讲清楚的技术判断。

### 2. 为什么用 RRF 融合而不是加权求和分数？

向量余弦相似度在 0~1 之间，BM25 分数可以到几十，**量纲完全不同**。
若直接加权求和，就必须先做归一化，而归一化方式（min-max？z-score？）
会引入额外超参，且不同 query 的分数分布还不稳定。

RRF（Reciprocal Rank Fusion）只用**名次**：

$$\text{score}(d) = \sum_i \frac{w_i}{k + \text{rank}_i(d)}, \quad k = 60$$

无需标定即可稳定工作，这也是工业界混合检索的常见默认方案。
代码里同时保留了 `weighted_fusion` 作为对照实现，方便做实验比较。

### 3. 为什么召回 top20 再重排到 top5？

粗排（向量/BM25）追求「别漏」，精排（cross-encoder）追求「排准」。
cross-encoder 把 (query, doc) 拼在一起过模型，能建模细粒度交互，排序质量明显更好，
但计算量是 $O(\text{候选数})$ 次前向推理，不能对全库做。

所以采用「召回宽、精排窄」的两段式：粗排 20 条候选成本极低，
精排只对这 20 条算分，兼顾质量与延迟。这个权衡在报告里以「hybrid vs hybrid_rerank」
的指标差与延迟差同时呈现。

### 4. 为什么把「拒答」做成一等公民？

RAG 最大的风险不是答不好，而是**答得很像真的但没有依据**。
本项目的拒答有两道闸门：

1. **检索闸门**：命中为空，或最优证据分低于 `REFUSAL_SCORE_THRESHOLD` 时，
   直接返回「未找到依据」，**根本不调用大模型**（省钱且不给它编造的机会）；
2. **生成闸门**：提示词要求模型在证据不足时输出固定标记 `NO_ANSWER`，
   服务层识别后统一转成用户可读的拒答文案。

评估集里专门设了 3 条 `should_refuse` 的越界问题（ImageNet 准确率、
某篇并不在库里的论文、食堂开门时间），用来量化拒答准确率。

### 5. 为什么不用 LangChain 的 RetrievalQA / ChatModel？

这是一个刻意的取舍，而不是「没用 LangChain」：

- **用了**：`langchain-core` 的 Embeddings 协议（所有向量后端实现它）、
  `langchain-text-splitters` 用于切分侧校验、`langchain-chroma` 作为对照实现。
- **没用**：`RetrievalQA` 这类高层链，以及 ChatModel 封装。原因有两条：
  (1) 混合检索需要自己控制两路召回与融合，高层链反而要绕开它的默认行为；
  (2) 生成端各大厂商全是 OpenAI 兼容的 `/chat/completions`，
  自己写 40 行客户端即可通吃 DeepSeek / 硅基流动 / 通义 / vLLM / Ollama，
  少一层抽象，流式解析与超时控制也更直接。

**面试时可以这样回答**：「框架用在该用的地方（协议、切分、向量库适配），
但核心检索链路自己实现，因为需要精确控制融合与重排，也为了能解释每一行为什么这样写。」

### 6. 为什么 chunk 要带 `section_path`？

因为**引用必须可定位**。只给文件名，学生无法核对结论；
给出「第 3 章 决策树 > 3.2 信息熵与信息增益 > 3.2.4 信息增益的缺陷」，
就能直接翻到对应段落。切分器在解析标题层级时就维护了这个路径，
所以这是「解析阶段」而不是「展示阶段」的设计决策。

### 7. 为什么建索引与查询用同一套 Chunk 对象？

`chunk_id` 由 `sha1(source_path::index::text[:64])` 生成，是**稳定且内容相关**的：
重建索引后同一片段 ID 不变，因此引用链接、评估集标注、去重逻辑都不会失效。
向量库存元数据时也一并写入 `section_path` / 行号，使得检索结果无需回查原文即可展示定位。

### 8. 多后端可插拔是怎么做的？

两处最容易被供应商绑死的地方都抽成了配置：

| 位置 | 可选后端 | 切换方式 |
| --- | --- | --- |
| 向量化 | local / siliconflow / dashscope / openai / hash | `EMBEDDING_PROVIDER` |
| 重排 | local cross-encoder / 云端 rerank API / 关闭 | `RERANK_PROVIDER` |
| 生成 | 任意 OpenAI 兼容端点 | `LLM_PROVIDER` + `LLM_API_BASE` |

`hash` 后端（确定性哈希伪向量）是刻意保留的：它没有语义能力，
但让单元测试和 CI 能在**不下载模型、不联网**的情况下跑完整条链路。
这是工程可测性的设计，不是玩具。

## 三、可观测性

一次检索会产出 `RetrievalTrace`：

```json
{
  "query": "信息增益为什么偏向取值多的属性",
  "dense_hits": 20, "sparse_hits": 20, "fused_hits": 20, "final_hits": 5,
  "rerank_used": true,
  "stage_ms": {"dense": 12.4, "sparse": 1.8, "fusion": 0.3, "rerank": 210.5}
}
```

前端右侧面板把它可视化（各路召回条数、融合候选数、检索总耗时），
每条召回片段还带 `channel` 与 `sub_scores`（该片段在各路的原始分与名次），
因此可以回答「为什么这条被召回」以及「重排前后名次怎么变的」。

## 四、已知局限与后续改进方向

诚实地列出局限，比声称「完美」更可信：

1. **PDF 解析质量依赖文本层**：扫描件（图片型 PDF）需要接 OCR，当前不支持；
2. **表格与公式的切分会被打断**：Markdown 表格跨 chunk 时会失去表头上下文，
   后续可做「表格整体不切分」的特殊处理；
3. **BM25 索引是纯内存的**：十亿级片段需要换 Elasticsearch / Milvus 稀疏索引；
4. **没有查询改写**：多轮对话中的指代（「它」「这个」）目前依赖 history 传入，
   可以加一步 LLM 改写或 HyDE；
5. **评估集规模有限**：38 条样本足以发现方案之间的差异，但要下定论需要几百条，
   并且应当加入人工标注的一致性检查（Cohen's kappa）；
6. **裁判与被测模型同源**：LLM-as-judge 存在自我偏好，严格评估应引入人工评分对照。
