# CourseRAG · 课程知识库问答系统

> 面向《机器学习导论》课程的专属答疑助手：把课程讲义、实验手册与 FAQ 变成可检索的知识库，
> 学生提问时给出**带章节级引用**的回答，证据不足时**明确拒答**。

这不是「调通 LangChain 示例」项目。重点在**可量化的检索效果**与**工程完备度**：
同一份标注评估集上跑消融实验，用数据说明了每一层设计（混合检索、精排、拒答）各自带来什么。

---

## 一、核心特性

| 能力 | 说明 |
| --- | --- |
| **全链路 RAG** | 文档解析 → 文本切分 → 向量化 → 混合检索 → 重排 → 带引用生成，每一环都有独立模块与测试 |
| **混合检索** | BM25 稀疏检索 + 向量稠密检索，RRF 加权融合（只用名次，免疫量纲差异） |
| **Cross-Encoder 重排** | 召回 top-20 → 精排 top-5，建模 query-doc 细粒度交互 |
| **引用可溯源** | 每个结论标注 `[n]`，可定位到「第 3 章 > 3.2.4 信息增益的缺陷」，行号一并入库 |
| **主动拒答** | 两道闸门：检索分低于阈值直接拒答（不调模型）+ 提示词要求证据不足时输出 `NO_ANSWER` |
| **可量化评估** | 38 条标注样本，Hit@k / MRR / nDCG / Recall 四项指标 + LLM-as-Judge 生成质量打分 + 消融实验 |
| **多后端可插拔** | 向量化/重排/生成三处均可切换本地或云端，**改 `.env` 即可，不动代码** |
| **完整工程化** | FastAPI 服务 + SSE 流式输出 + 检索调试接口 + CLI 工具 + Docker + 50+ 单元测试 |
| **离线可测** | 内置确定性哈希向量后端，CI 里无需下载模型即可跑完整链路测试 |

## 二、架构

```
data/raw/*.md|txt|pdf|docx
        │
   ┌────▼────┐   ┌──────────┐   ┌──────────────────┐
   │ 解析     │──▶│ 切分      │──▶│ 向量化 → Chroma   │──┐
   │ loader  │   │ chunker  │   └──────────────────┘  │ top20
   └─────────┘   └────┬─────┘   ┌──────────────────┐  │
                      └────────▶│ BM25 稀疏索引      │──┤ top20
                                └──────────────────┘  │
                                          ┌───────────▼───────────┐
                                          │ RRF 加权融合 → top20   │
                                          └───────────┬───────────┘
                                          ┌───────────▼───────────┐
                                          │ Cross-Encoder → top5  │
                                          └───────────┬───────────┘
                                          ┌───────────▼───────────┐
                                          │ 带引用生成 / 拒答      │
                                          └───────────┬───────────┘
                                                      ▼
                                       答案 + [n] 引用 + 召回明细 + 链路耗时
```

设计理由与取舍详见 **[docs/architecture.md](docs/architecture.md)**（含「为什么用 RRF」
「为什么不用 RetrievalQA」「拒答为什么是两道闸门」等 8 个决策的完整解释）。

## 三、快速开始

### 1. 环境

```bash
cd rag
python -m venv .venv
.venv\Scripts\activate            # Windows
# source .venv/bin/activate       # macOS / Linux

pip install -r requirements.txt   # 核心依赖 + 本地模型（torch 为 CPU 版，约 200MB）
```

>
> **① 编码**：`requirements*.txt` 里有中文注释，pip 用系统默认编码（GBK）读取时会报
> `UnicodeDecodeError: 'gbk' codec can't decode`。先设一次环境变量即可：
> ```powershell
> $env:PYTHONUTF8=1; $env:PYTHONIOENCODING='utf-8'
> ```
>
> **② 镜像源**：清华 TUNA 镜像目前**无法解析 langchain**（实测返回空，
> 官方 PyPI 与阿里云、腾讯云均正常）。若安装卡在 langchain，换源：
> ```powershell
> pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/
> ```
>
>若 只想快速验证流程、不想装深度学习依赖：
> `pip install -r requirements-core.txt`，然后在 `.env` 里把 `EMBEDDING_PROVIDER` 设为 `hash`
> （哈希伪向量，无语义能力但可跑通全链路）。

### 2. 配置

```bash
copy .env.example .env      # Windows
# cp .env.example .env      # macOS / Linux
```

默认配置**不需要任何 API Key**：本地 BGE 向量模型 + 本地重排模型，生成端自动降级为抽取式摘要。
想要生成式回答，在 `.env` 里填一项即可：

```ini
LLM_PROVIDER=deepseek
LLM_API_BASE=https://api.deepseek.com/v1
LLM_MODEL=deepseek-chat
LLM_API_KEY=sk-你的key      # 填了这一行，回答立刻变成生成式
```

（也可以用硅基流动、通义、任意 OpenAI 兼容端点，见 `.env.example` 注释。）

### 3. 建索引

```bash
python -m scripts.build_index
```

输出示例：

```
第 1 步 · 文档解析      共 9 篇文档，合计 39483 字
第 2 步 · 文本切分      174 个片段，平均 227.8 字，100% 带章节路径
第 3 步 · 向量化入库    写入 174 条向量（local:BAAI/bge-small-zh-v1.5）
第 4 步 · BM25 索引     174 条，分词+建索引 0.6s
```

### 4. 提问

```bash
# 命令行
python -m scripts.ask "信息增益为什么会偏向取值多的属性"
python -m scripts.ask --mode dense "SVM 的 C 参数怎么影响模型"     # 对比不同检索模式
python -m scripts.ask --show-context "PCA 为什么要用特征向量解释"  # 打印召回片段与分数

# Web 界面（含流式输出、引用点击跳转、检索链路面板）
python -m scripts.serve
# 打开 http://127.0.0.1:8000/
```

### 5. 评估

```bash
python -m scripts.evaluate --retrieval-only   # 只看检索，不需要 Key
python -m scripts.evaluate                    # 检索 + 生成质量（需 Key）
```

报告同时落到 `data/eval/reports/*.json`（给程序读）与 `*.md`（给人读）。

## 四、评估结果

这是本项目最重要的部分。评估集 38 条人工标注样本（含 3 条越界拒答样本），
知识库 12 篇课程资料 → 241 个片段（recursive，size=500 / overlap=80）。

> 片段数从最初的 283 降到 241，是因为修掉了一个隐藏很深的切分缺陷（见 4.4 节）。
> **这个修复说明：先用被污染的数据得出的结论是不可靠的**。

### 4.1 主结果：查询改写 + 混合检索 + 精排（片段级严格口径）

标签精确到「文档 + 章节路径」，并排除只复述问题、不含答案的大纲小节。

| 检索方案 | Hit@1 | Hit@3 | Hit@5 | MRR | Recall@5 | nDCG@5 |
| --- | --- | --- | --- | --- | --- | --- |
| 仅向量检索 (dense) | 0.600 | 0.914 | 0.943 | 0.754 | 0.779 | 0.701 |
| 仅 BM25 (sparse) | 0.543 | 0.943 | 1.000 | 0.748 | 0.860 | 0.728 |
| **混合检索 RRF** | **0.657** | 0.943 | 0.971 | **0.806** | 0.821 | **0.750** |
| 混合检索 + 重排 | 0.600 | **0.971** | **1.000** | 0.779 | **0.843** | 0.740 |

**怎么读**：`Hit@5` 已接近饱和（重排后 100%），说明**召回覆盖不再是瓶颈**，
所以用 `Hit@1` 与 `MRR` 判断谁更好——混合 RRF 在这两项上最优。
重排的价值体现在 `Hit@3/@5` 与 `Recall@5`：它把「本来在候选池里但排得靠后」的正确答案提上来。

### 4.2 三个关键消融：每一项都用数据决定，而不是靠感觉

**(1) 查询改写：收益最大的一项**

| 配置 | Hit@1 | MRR | nDCG@5 |
| --- | --- | --- | --- |
| 改写关闭 | 0.429 | 0.649 | 0.619 |
| **改写开启** | **0.657** | **0.806** | **0.750** |
| 变化 | **+53%** | **+24%** | +21% |

原因见 4.5：学生用口语提问、教材用术语书写，两者不重合时召回会**整段漏掉**。

**(2) 融合策略：RRF vs 加权分数融合**

| 融合方式 | Hit@1 | MRR | nDCG@5 |
| --- | --- | --- | --- |
| **RRF（默认）** | **0.429** | **0.649** | **0.619** |
| 加权分数融合 | 0.400 | 0.642 | 0.618 |

我把默认改成加权融合，因为它在**当时的**数据上四项指标都更好——
但那个「更好」是**被污染数据造成的假象**（见 4.4）。修掉空壳片段后重测，
加权融合在两个评估集、四项指标上全面落后，于是改回 RRF。

**加权为什么反而更差**：`min-max` 归一化会把**每一路的最高分都拉成 1.0**，
于是「在弱的一路里碰巧排第一」的无关片段拿到满分，
而「在强的一路排第 3」的真答案反被压低。
实测有查询的正确答案因此从**第 7 名掉到第 18 名**。

**(3) 重排：质量换延迟**

重排把 MRR 从 0.649 提到 0.694（+6.9%）、Recall@5 从 0.759 提到 0.843（+11%），
代价是延迟从约 18 ms 涨到约 1.2 s（**约 65 倍**）。三种调节手段见 4.6。

### 4.3 生成质量（LLM-as-Judge，真实模型）

| 指标 | 分数 | 说明 |
| --- | --- | --- |
| 忠实度 faithfulness | **5.0 / 5** | 回答的每条事实性陈述都能在片段中找到依据 |
| 相关性 answer_relevance | **5.0 / 5** | 正面且完整地回答问题 |
| 引用正确性 citation_correctness | **5.0 / 5** | `[n]` 标注与结论一致 |
| 拒答准确率 | **1.00** | 3 条越界问题全部正确拒答，**零误拒** |
| 检出幻觉 | **0 条** | 38 条样本均未发现无依据陈述 |
| 打分覆盖 | 38/38 | 单条失败不中断整轮（见下） |

裁判提示词最初过于宽松（38 条全给满分，等于没有区分度）。
改为**要求逐句核对、明确各分值的门槛、并说明「给 5 分是有门槛的」**之后，
裁判开始能抓出问题——例如它准确指出模型自行补充过一句片段中没有的机制解释并扣分。

**评估的健壮性也补了一课**：第一次跑生成评估时，一次网络超时让整轮崩溃、
38 条样本的结果全部丢失。修复两处：
① LLM 客户端对连接超时与 5xx/429 做指数退避重试（4xx 不重试）；
② 单条样本失败只记录原因并继续，不再中断整轮。
修复后本轮 38/38 全部打分成功。

> 裁判与被测模型同源，存在自我偏好，这是已知局限，严格评估应引入人工基线。

### 4.4 修掉的一个隐藏缺陷：15% 的片段是「空壳」

**现象**：283 个片段里有 **43 个（15%）只有一行标题、没有正文**，例如：

```
len=15  第 8 章 无监督学习 > 8.3 如何选择簇数 K
内容:   ## 8.3 如何选择簇数 K
```

**危害机制**（这是最难发现的地方）：

1. 空壳只含标题词，与提问的**字面重合度极高**，因此排序上很有竞争力；
2. 它会**挤掉真正含答案的兄弟章节**——`8.3.1 肘部法`、`8.3.2 轮廓系数法` 全被挡在候选之外；
3. 即使空壳进了上下文，模型看到的也只是一行标题，
   于是**合理地拒答**——「K-means 里 K 该怎么选？」就是这样被误判为无依据的。

**根因**：切分器为每个 section 都产出 chunk，而「含子标题的父标题」本身没有正文。
**修复**：新增 `is_shell_text()`，正文为空（只有标题行）的 section 不产出 chunk，
并在 `chunk_document` 统一过滤 + 重新连续编号。

**它还是我得出错误结论的原因**：融合策略对照实验是在含空壳的索引上跑的，
所以加权融合「赢」了。数据不干净时，优化方向也会错——
**先修数据质量，再比方案**。

### 4.5 另一个真实失败：口语化提问召回不到

**现象**：学生问「K-means 里 K 该怎么选？」，系统拒答。
但知识库里明明有 `8.3 如何选择簇数 K`（含肘部法、轮廓系数法、Gap Statistic）。

**逐层定位**（不是猜）：

| 环节 | 结果 |
| --- | --- |
| 稠密检索 top20 | 目标章节第 **17** 名 |
| BM25 top20 | 第 **14** 名 |
| RRF 融合 | 第 7 名（勉强进候选池） |
| 精排后 | 第 8 名 |
| 最终 top5 | **未进入** |

**根因**：提问是抽象口语句式（「K 该怎么选」），语料是教材用语
（「如何选择簇数 K」「肘部法」「轮廓系数法」），两路召回都够不着。
**模型拒答是正确的**——它确实没有依据。

**修复**：实现查询改写（`ENABLE_QUERY_REWRITE`），用一次很便宜的模型调用
把口语问题扩写成教材式检索式：

```
问：K-means 里 K 该怎么选？
改写：K-means 如何选择簇数 K 肘部法 轮廓系数 Gap Statistic
→ 目标章节从「未召回」变成第 2 名

问：为啥训练集准测试集不准
改写：过拟合 泛化误差 训练误差 验证集
→ 目标章节从「未召回」变成第 4 名
```

改写失败会**自动回退原问题**，绝不让检索因此失败。整体收益见 4.2 (1)。

### 4.6 延迟与质量的权衡

| 配置 | 平均延迟 | 适用场景 |
| --- | --- | --- |
| 仅 BM25 | **1 ms** | 延迟极敏感的输入联想 |
| 混合 RRF（含改写） | ~1.4 s（改写占绝大部分） | 质量优先，改写可缓存 |
| 混合 + 重排（含改写） | ~3.0 s | 课程答疑，可接受 |

重排与改写是两笔独立的成本。想省延迟时的调节顺序：
① 关改写（质量损失最大，不推荐）；② 减小 `RERANK_CANDIDATE_POOL` / `RERANK_MAX_CHARS`；
③ 换云端 rerank 接口（`RERANK_PROVIDER=api`）。

### 4.7 复现方式

```bash
python -m scripts.build_index                                       # 建索引（约 20s）
python -m scripts.evaluate --retrieval-only --granularity section    # 检索消融（无需 Key）
python -m scripts.evaluate --rewrite                                # 改写 + 生成质量（需 Key）
python -m scripts.calibrate                                          # 标定拒答阈值
```

完整报告（含逐题明细、错误分析、幻觉清单）：`data/eval/reports/`。

### 4.2 同一批数据、换一种判定口径，结论会反过来

同一套方案、同一批问题，只把「命中」的判定从章节级放宽到文档级：

| 方案 | Hit@1 | MRR | Recall@5 | nDCG@5 |
| --- | --- | --- | --- | --- |
| 仅向量检索 (dense) | 0.543 | 0.763 | 1.000 | 0.822 |
| 仅 BM25 (sparse) | 0.429 | 0.691 | 0.986 | 0.760 |
| 混合检索 RRF (hybrid) | 0.486 | 0.733 | 1.000 | 0.799 |
| 混合检索 + 重排 (hybrid_rerank) | **0.571** | **0.764** | 1.000 | **0.825** |

宽松口径下的解读是「重排只把 MRR 从 0.763 提到 0.764（+0.2%），完全不值得 5 倍延迟」；
严格口径下同一组实验是「**MRR +6.9%、Recall@5 +9.7%**，每项都最优」。差异的来源：

语料里的《课程大纲与学习指南》有一节「各章核心问题」，逐条列出的正是评估集里的问题原句
（例如「ID3、C4.5、CART 三代算法的差别在哪？」），但**不含答案**。
它与问题字面高度重合，因此稳定排第一，被「文档级」判定算作命中——
于是「把不含答案的小节排第一」这件事被指标系统性地掩盖了。

> **这是我认为最值得讲的一条经验**：RAG 项目里「检索没做好」和「指标没量准」长得一模一样，
> 而后者更危险——它会让你去优化一个并不存在的问题。
> 因此本项目保留两种口径的评估集（`eval_set.jsonl` / `eval_set_chunk.jsonl`），
> 用两者的差值暴露判定口径带来的偏差。

### 4.3 延迟与质量的权衡

重排把延迟从 216 ms 提到约 1.1 s（CPU 上约 5 倍），换来 MRR +6.9%。
这是一个**明确标注了代价**的取舍，而不是只报收益。四种调节方式（均可配置）：

| 做法 | 效果 |
| --- | --- |
| 减小 `RERANK_CANDIDATE_POOL`（默认 10） | 线性降低重排耗时，候选越少收益越低 |
| 减小 `RERANK_MAX_CHARS`（默认 320） | cross-encoder 成本随长度二次增长，截断最有效 |
| `RERANK_PROVIDER=api` 换云端 rerank | 可降到百毫秒级，代价是外部依赖与费用 |
| 纯 BM25 兜底 | 1 ms、MRR 0.618，适合延迟极敏感的输入联想场景 |

### 4.4 拒答阈值标定（`scripts/calibrate.py`）

拒答阈值不能凭感觉设。脚本在评估集上统计两类的**证据分分布**，并给出不同阈值下
「误拒库内问题」与「漏放越界问题」的代价：

```
知识库内问题   n=35   min=0.481  中位=0.692  max=0.792
越界问题       n=3    min=0.396  中位=0.410  max=0.556

阈值       误拒库内     漏放越界     说明
0.481      0/35        1/3         最保守：不误拒任何库内问题
0.556      1/35        0/3         错误总数最少
```

**结论：两类分数存在重叠，单靠阈值无法完全分开。** 越界问题里最难挡的是
「这个模型在 ImageNet 上的准确率是多少」——它本身是标准的机器学习问题，
与课程语料语义高度接近（0.556）；而「课程成绩是怎么算的」这种库内问题只有 0.481。

因此本项目**默认不设阈值**（`REFUSAL_SCORE_THRESHOLD` 留空）：
检索侧只拦「一条都没召回」的情况，语义拒答完全交给生成侧的 `NO_ANSWER` 闸门。

> 这是一次**有意识的取舍**：设成 0.481 会漏放 1/3 的越界问题，
> 设成 0.556 会误拒 1/35 的正常问题。考虑到「问了课程内的问题却被拒答」
> 对体验的伤害更大，且越界样本只有 3 条、统计不稳健，我选择不做阈值拦截。
> 若业务更不能容忍幻觉，把这一行改成 `REFUSAL_SCORE_THRESHOLD=0.481` 即可。

### 4.5 生成质量（LLM-as-Judge）

裁判对每个回答打三项 1~5 分：忠实度（是否全部有据可依）、相关性、引用正确性，
并要求列出「无法从片段推出的句子」作为幻觉证据。命令：`python -m scripts.evaluate`。

未配置 `LLM_API_KEY` 时这部分会**自动跳过并在报告中标注，不会伪造分数**——
本项目默认配置就是无 Key 的本地档，因此仓库里的报告文件这一节为空。

### 4.6 复现方式

```bash
python -m scripts.build_index                                      # 建索引（约 20s，首次需下模型）
python -m scripts.evaluate --retrieval-only --granularity section   # 主结果表
python -m scripts.evaluate --retrieval-only --granularity document  # 对照口径
python -m scripts.calibrate                                         # 标定拒答阈值
```

完整报告（含逐题明细与错误分析）：`data/eval/reports/report-20261004-211301-FINAL-section.md`。

## 七之补：开发过程中踩到并修掉的坑

这一节记录真实的调试过程——面试官往往更关心「你怎么定位问题」，而不是「你用了什么框架」。

### 1. 稀疏检索静默失效（最危险的一类 bug）

现象：命令行提问时 `trace.sparse_hits = 0`，但单独调用 BM25 索引能正常返回结果。

根因：`HybridRetriever` 直接构造时，`BM25Index` 是空的——只有测试和评估脚本自己手动
`load()` 了缓存，CLI 与服务入口都没加载。**更糟的是它不报错**，
只是悄悄退化成「只有一路向量检索」，指标看起来还正常。

修复：把「确保索引可用」下沉到 `BM25Index.ensure_loaded()`（先读缓存，
缓存缺失则从向量库导出重建），并在构造 `HybridRetriever` 时调用。
同时补了回归测试 `test_ensure_loaded_fills_empty_index_from_cache`。
**教训**：多路召回里任何一路为空都必须能观测到，所以 `RetrievalTrace` 里专门记了
`dense_hits` / `sparse_hits`。

### 2. 重排把延迟拖到 44 秒/query

现象：消融实验里 `hybrid_rerank` 平均延迟 **44517 ms**，其他方案只有几百毫秒。

定位过程（分层计时，而不是猜）：
1. 先用 `RetrievalTrace.stage_ms` 确认耗时全在 `rerank` 阶段（3.7~16.8 s），不在检索；
2. 单独压测 `CrossEncoder.predict`：20 对短文本只要 **423 ms**，说明模型本身没问题；
3. 于是怀疑加载环节 —— 日志里果然有 5 次 `huggingface.co/api/models/.../commits/main` 超时重试。

根因：模型已缓存在本地，但每次构造 `CrossEncoder` 仍会去 huggingface.co 查版本，
国内网络下连着重试超时。修复：检测到模型已缓存时强制 `HF_HUB_OFFLINE=1`。
**延迟从 44.5 s 降到约 2 s。**

### 3. 重排耗时的真正来源：输入长度（二次增长）

修完网络问题后仍是 ~2 s。继续压测得到明确规律：

| 送进模型的文本长度 | 20 对耗时 |
| --- | --- |
| 截断到 128 字 | 1081 ms |
| 截断到 256 字 | 2146 ms |
| 不截断（最长 492 字） | 3618 ms |

cross-encoder 的注意力成本随序列长度二次增长，这是 CPU 上的硬约束。
因此做了三项工程取舍（全部可配置）：候选池 20→10、送模型文本截断到 320 字、
batch_size 从默认 32 调到 8（实测 CPU 上小 batch 更快：4 比 32 快约 30%）。
最终稳定在 **约 1.1 s/query**，并在 README 里如实报告「5 倍延迟换 Hit@1 +5.2%」。

### 4. 评估报告本身有两处 bug

- 报告自动生成的「最优方案」取了 `Hit@5` 最大者，而 `Hit@5` 全部并列 1.0，
  于是永远选出第一个方案（dense）。改为按 `MRR` / `Hit@1` 判优，并区分「单路基线」与「两段式方案」。
- 逐题明细 `per_sample` 只用于内存计算、没有写进 JSON，
  导致错误分析永远显示 `0/0`。修复后错误分析才真正可用（dense 有 16/35 条未排第一）。

**教训**：评估脚本也需要被审查——一个算错的指标比没有指标更危险。

### 5. 无 Key 降级路径把内部标记泄露给用户

现象：`pipeline.answer()` 在抽取式降级分支返回了模型的内部拒答标记 `NO_ANSWER`，
直接显示给学生。

修复：降级分支识别 `refused` 后统一替换成用户可读的拒答文案（与生成式分支一致），
流式分支同样处理。由 `test_refusal_when_no_evidence` 守住这个行为。

### 6. 代码块里的 `#` 注释被当成了 Markdown 标题

现象：实验手册的代码块里有 `# 建议使用独立的虚拟环境`、`# 用交叉验证选出最优的 ccp_alpha`
这类 Python/Bash 注释。切分器按 `^#{1,6}\s+` 找标题，于是把它们当成了章节标题，
chunk 带上了**根本不存在的章节路径**——引用会指向错的地方，而这个问题不会报错。

修复：切分前先扫描围栏代码块（``` / ~~~），把块内行对「标题识别」屏蔽掉，
但正文仍取自原文，保证代码与公式原样保留。补了两个回归测试
（`test_code_fence_comments_are_not_treated_as_headings`、
`test_heading_inside_fence_does_not_split_sections`）。

**教训**：解析器必须对真实文档的写法做防御——讲义、README 里到处是代码块，
这是最容易埋且最难发现的静默错误。

### 7. 评估口径本身把指标算高了（最值得讲的一条）

现象：按「文档级」判定命中时，多个问题的 rank-1 是
`00-课程大纲与学习指南.md > 各章核心问题 > 第 3 章 决策树`。

排查后发现：那一小节的原文是「信息熵、条件熵、信息增益……ID3、C4.5、CART 三代算法的差别在哪？」
——**它逐条复述的正是我评估集里的问题本身，但不含任何答案**。
由于与问题字面高度重合，它稳定地排在第一位，而「文档级」判定把这种命中算作正确。

修复：新增片段级评估集 `eval_set_chunk.jsonl`，标签精确到「文档 + 章节路径」，
并显式排除只复述问题的大纲小节；评估器按 `(source_path, section_path)` 二元组判定命中。
两种口径的结果都保留，用差值来暴露原口径的高估程度。

**这是本项目最有价值的一条经验**：RAG 项目里，「检索没做好」和「指标没量准」
经常长得一模一样，而后者更危险——因为它会让你去优化一个并不存在的问题。

## 九、已知局限

1. **无 Key 时拒答能力是打折的**：默认的抽取式降级模式只能靠词汇重合判断，
   对「用课程术语包装但库里没有答案」的问题（例如问一篇并不在库中的论文）
   会返回片段摘要而非拒答。**生成侧的语义拒答闸门只有在配置 `LLM_API_KEY` 后才真正生效。**
   这是刻意的取舍：宁可让无 Key 的演示链路完整可跑，也不假装它具备完整的拒答能力
   （行为已由 `test_extractive_mode_limitation_on_out_of_scope_but_lexically_close_question` 固定）。
2. **扫描件 PDF 需要 OCR**，当前只支持有文本层的 PDF；
3. **Markdown 表格跨 chunk 时会丢表头上下文**（切分器已能正确识别代码块与标题，
   但未对表格做「整体不切分」保护）；
4. **BM25 索引在内存中**，千万级以上片段需换 Elasticsearch / Milvus；
5. **评估集只有 38 条**，足以对比方案差异，但要下结论建议扩到数百条，
   并加入人工评分与 LLM 裁判的一致性检查（如 Cohen's kappa）；
6. **LLM-as-Judge 与被测模型同源时存在自我偏好**，严格评估应引入人工基线；
7. **RRF 权重是默认的 1:1**，没有针对本语料做搜索；从消融数据看，
   调权重很可能还能再挤出一些收益，但那是过拟合评估集的风险动作，我选择不做。
