# 架构与关键设计决策

面向面试的说明文档：解释「为什么这样设计」，而不是「代码怎么写」。

> 主循环有**两份等价实现**：手写 `while`（`runtime/agent.py`，默认）
> 与 LangGraph 状态图（`runtime/langgraph_agent.py`，可选）。
> 本节的流程图描述的是两者**共同的语义**；为什么要保留两份，见 §2.9。

## 一、主循环

```
                    任务（自然语言）
                          │
                 ┌────────▼────────┐
                 │  组装系统提示词  │  工具清单 + 行为约束 + 输出要求
                 └────────┬────────┘
                          │
        ┌─────────────────▼─────────────────┐
        │         Agent 主循环              │
        │                                   │
        │   ┌───────────────────────────┐   │
        │   │ 防护检查（步数/时长）      │   │◀── 每轮先检查，再决策
        │   └─────────────┬─────────────┘   │
        │                 │                 │
        │   ┌─────────────▼─────────────┐   │
        │   │ 决策（function calling）   │   │──► 直接回答 ──► 结束
        │   └─────────────┬─────────────┘   │
        │                 │ 要调工具         │
        │   ┌─────────────▼─────────────┐   │
        │   │ 防护：重复调用检测         │   │◀── 同名同参 → 注入提醒
        │   └─────────────┬─────────────┘   │
        │   ┌─────────────▼─────────────┐   │
        │   │ 执行工具（失败转结果）      │   │
        │   └─────────────┬─────────────┘   │
        │   ┌─────────────▼─────────────┐   │
        │   │ 防护：连续失败计数         │   │◀── 超阈值 → 要求作答
        │   └─────────────┬─────────────┘   │
        │                 │                 │
        │      回填观察结果进对话历史        │
        └─────────────────┬─────────────────┘
                          │
                    完整 Trace（可回放）
```

## 二、关键设计决策与理由

### 1. 为什么工具失败必须转成「结果」而不是抛异常

Agent 的价值恰恰体现在「看到失败后改变策略」。
如果工具报错就让整个流程崩掉，那这个系统只是「带工具的问答」而不是 Agent。

所以 `ToolRegistry.invoke` 把三类问题全部包成 `ToolResult(ok=False)`：

- 工具不存在 → 提示可用工具清单，模型可以立刻改用正确的；
- 参数不合法 → 指出缺哪个、哪个是未定义的，模型可以修正参数；
- 工具内部异常 → 返回异常类型与最后一行堆栈，模型可以判断是否换个思路。

**失败信息要「可行动」**：只说「调用失败」模型无从下手，说清「缺少必填参数 query；
可用参数：query, top_k」它就能自己纠正。

### 2. 五种防护为什么是一等公民

Agent 失控不是小概率事件，而是默认行为——只要模型认为「再查一次会更好」，
它就会一直查下去。所以防护不是「加个 if」，而是主循环的结构：

| 机制 | 拦住的失控情形 | 触发后的动作 |
| --- | --- | --- |
| `max_steps` | 无限循环 | 停止，标记 `max_steps` |
| `max_seconds` | 单任务挂太久 | 停止，标记 `timeout` |
| `repeat_tolerance` | 原地打转 | 先注入提醒；仍不改则 `no_progress` |
| `max_consecutive_failures` | 硬试失败工具 | 注入「直接作答」指令 |
| `max_observation_chars` | 上下文被撑爆 | 裁剪并明确告知「已截断」 |

**为什么「原地打转」要先生成步骤再停**：直接停会让用户看到「突然失败」，
而注入提醒后模型往往能自己改过来——这本身就是 Agent 该有的自我纠正能力。
只有提醒后仍重复才判定无进展。

**「重复」的判据是「同名同参」，不是「同名」。** 签名定义在 `app/schema.py`：

```python
def signature(self) -> str:
    """用于检测「原地打转」：同名同参视为重复调用。"""
    items = sorted((k, str(v)) for k, v in self.arguments.items())
    return f"{self.name}({items})"
```

这区分了两种行为：模型**换关键词重搜**是正常的检索策略（签名不同，不计入重复）；
**用同一个参数反复调同一个工具**才是失控（结果永远不变，纯粹烧 token）。

`repeat_tolerance` 默认 **2**，触发条件是 `count > repeat_tolerance`——
即**同一个签名出现到第 3 次**才判定失控：第 3 次注入提醒让模型自救，
到第 4 次（`count > tolerance + 1`）才把 `stop_reason` 置为 `no_progress` 并终止。
留这 2 次余量是刻意的：换个角度再查一次属于合理探索，第 2 次就拦会误伤正常策略。

其余四个阈值：`max_steps=12`、`max_seconds=180`、`max_observation_chars=4000`、
`max_consecutive_failures=4`。

> **真实模型下这五种防护一次都没触发过**（评估报告里「防护触发率 0.0%」）。
> 这不是缺陷，也不必粉饰：12 条任务集只有 6 easy + 6 medium、没有 hard，
> 任务本身偏简单（重复运行时会看到成功率在 91.7%~100% 之间波动，
> 也印证了样本量与难度都不足以支撑一个稳定的高分区）。
> **防护的价值在兜底，而兜底逻辑只能靠假大脑构造边界单测来验证**——
> 「连续 3 次用同一参数调同一工具」这种场景真实模型跑不出来。
> 同理，工程层指标里的「失败恢复率」当前显示 `0.0%`，但它的分母是**全部 12 条任务**，
> 而不是「发生过工具失败的任务」——这一轮 `failed_tools 0`，没有任何失败可供恢复，
> 于是 `0.0%` 会被误读成「自我纠正能力为零」。**分母取错，这个指标就应该显示 `N/A`。**
> 要让它真正有分母，需要在任务集里主动注入工具失败。
> （对比之下 `防护触发率` 用总任务数作分母是正确的——它问的就是「多少任务触发了防护」。）

### 3. 为什么用「单步决策」而不是「先出完整计划」

两种架构各有取舍：

| 架构 | 优点 | 缺点 |
| --- | --- | --- |
| Plan-and-Execute（先规划再执行） | 步骤可控、可预览 | 计划一旦错就整条错；工具报错后难以调整 |
| **ReAct（决策-观察-再决策）** | 能根据观察随时调整、天然容错 | 步数可能偏多，缺少全局视角 |

本项目选 ReAct，理由是工具集里有 `web_search` / `fetch_url` 这类
**结果高度不可预测**的工具——先规划好的步骤很可能因为抓取失败而作废。
ReAct 的「每步都重新看一遍现状」在这种场景下更稳。

代价是步数偏多，所以用 `max_steps` 与「信息够了就立即作答」的提示词来约束。

### 4. 轨迹为什么用 JSONL 而不是「一次运行一个文件」

评估要一次读几百条轨迹。JSONL 可以流式读取、追加写入、单行损坏不影响其余记录
（`test_store_survives_corrupted_line` 专门锁住这一点）。
一次运行一个文件会产生几百个小文件，读取时要管理文件句柄与排序，得不偿失。

同时额外维护一个 `index.jsonl` 摘要索引，前端列历史时不必读全量轨迹。

### 5. 为什么要有离线 mock 后端

没有密钥就不该能跑吗？我认为不该。mock 的存在让以下事情在没有 Key 时也能被验证：

- 工具注册、参数校验、失败兜底、输出裁剪是否正确；
- 主循环的五种防护是否真的会触发；
- 轨迹是否能完整落盘并回放；
- API、SSE 流式、前端渲染是否正常；
- 136 个单元测试不依赖网络与密钥（未安装可选的 LangGraph 时为 109 个）。

**但必须同时保证它不会被误读**：`preflight`、CLI、评估报告、API 响应里
都会显式标注当前是 mock 模式；评估报告更是把「工程层」与「能力层」拆成两栏，
能力层直接标「本次不可用」。这是我在上个项目（RAG）里学到的教训——
**一个没有标注清楚的降级模式，比没有降级模式更危险**。

### 6. 跨项目复用：`app` 包名冲突怎么解

两个项目都叫 `app`。若这么做：

```python
sys.path.insert(0, "../rag")
import app.retrieval.hybrid_retriever   # ← 可能解析到 agent-lab 自己的 app
```

结果是**部分模块来自另一个项目**，而报错位置与真实原因毫不相干。

正确做法（`course_rag_bridge.py`）：

1. **懒加载**：只在真正用到该工具时才加载，不拖慢普通启动；
2. **临界区隔离**：加载期间临时改 `sys.path`，同时清掉 `app.*` 的模块缓存；
3. **立刻还原**：`finally` 里恢复 `sys.path` 与模块缓存；
4. **明确报错**：路径不对或缺依赖时，给出「应该在 .env 里怎么改」的中文提示。

线程安全用锁保证（`get_course_rag` 双检锁），避免并发首次调用时重复加载。

### 7. 沙箱的能力边界（面试高频追问）

`run_python` 做了六件事：

1. 独立子进程（崩溃/死循环不影响主进程）；
2. `python -I` 隔离解释器（忽略环境变量与用户 site-packages）；
3. 超时强杀；
4. 独立工作目录 `data/workspace`；
5. **清空子进程环境变量**（`LLM_API_KEY` 绝不能泄漏给模型生成的代码，
   有测试专门验证这一点）；
6. stdout/stderr 长度限制。

**但不能声称这是安全沙箱**：它挡不住 `ctypes` 直接调用系统 API 这类蓄意逃逸。
生产环境应换成容器或微虚拟机。代码注释与 README 都写明了这条边界。

### 8. 评估判据为什么要包含 `forbid_tools`

只检查「有没有用该用的工具」会漏掉一类重要错误：
**明明课程资料里就有答案，却跑去联网**。这在成本、延迟、可靠性上都是退步
（联网更慢、可能失败、可能引入错误信息）。

所以评估集里专门有 `forbid_tools` 样本，把「工具使用的克制」也纳入量化。

### 9. 为什么同时保留手写循环和 LangGraph 两个引擎

同一套语义有两份实现（`runtime/agent.py` 与 `runtime/langgraph_agent.py`），
用 `AGENT_ENGINE` 切换，**默认仍是手写版**。这不是「为了用框架而用框架」，
而是一次有明确目的的重写。

**为什么不直接换成 LangGraph**：手写版的价值在于**零抽象**。
五种防护在一个 `while` 里逐条可见，讲清楚「Agent 为什么会失控」时它是更好的载体；
而且它不需要任何额外依赖——`pip install -r requirements.txt` 就能跑。

**那 LangGraph 版多出了什么**——只有两样，但都是手写版**结构上做不到**的：

| 能力 | 手写版 | LangGraph 版 |
| --- | --- | --- |
| 轨迹回放（事后看） | ✅ `TraceStore` + `scripts/traces.py` | ✅ 同样支持 |
| **从中断点续跑** | ❌ 做不到 | ✅ checkpointer |
| **危险工具人工审批** | ❌ 做不到 | ✅ `interrupt()` |

差别不在「谁更快」，而在**状态归谁管**。手写版的 `messages`、计数器、
防护状态都活在 `_iterate` 的局部变量里，函数一退出就没了——
所以 `TraceStore` 只能把历史**读出来展示**，无法「接着往下跑」。
LangGraph 把这些状态交给 checkpointer 按超步持久化，于是
「暂停 → 换人决策 → 继续」变成可能。

**行为等价是被断言保证的，不是靠自觉**：
`tests/test_langgraph_engine.py` 用同一个脚本化假大脑驱动两个引擎，
断言步骤序列、工具参数、防护标记、停止原因逐项一致；
`scripts/compare_engines.py` 还把这条断言搬到真实任务集上跑。

**代价也说清楚**：多一层抽象、多一组概念（State/Reducer/Checkpointer）、
多一个可选依赖。所以它没有取代手写版，而是并列存在——
**能讲清两者的取舍，本身就是这个项目想展示的东西**。

> 一个容易踩的坑：state 里**不能放 dataclass**。checkpointer 走 ormsgpack
> 序列化，塞 `Trace`/`Step` 对象会在运行时才炸。所以这里把步骤存成
> `Step.to_dict()` 的形状，需要 `Trace` 时复用 `trace_store._record_to_trace` 还原——
> **checkpoint 格式与落盘格式因此是同一套**，两条路不会各自漂移。

## 三、可观测性

三层观测，对应三种使用场景：

| 层级 | 载体 | 使用场景 |
| --- | --- | --- |
| 实时 | SSE `step` 事件 | 网页实验台看 Agent 正在干什么 |
| 事后 | `runs.jsonl` + `index.jsonl` | CLI 检索历史、按条件筛选、回放 |
| 批量 | 评估报告 JSON / Markdown | 量化对比不同提示词、工具组合的效果 |

## 四、已知局限与改进方向

1. **无长期记忆**：每次运行独立，不保留用户偏好与历史结论。
   可加「会话级摘要记忆」而不是存全量对话（后者会迅速吃掉上下文）。
2. **无显式计划树**：复杂任务上不如 Plan-and-Execute。
   改进方向是混合架构——先出粗粒度计划，执行时允许动态修订。
3. **评估集偏小**：12 条任务，判据以关键词为主。
   应扩到几十条并引入 LLM 裁判 + 人工抽检。
4. **无成本上限**：只统计 token，没有「单任务 token 超限即中止」的防护。
   生产环境应该有硬性预算。
5. **并发调用是「顺序执行」的**：一轮里模型可以返回多个 `tool_calls`，
   代码会逐个执行、逐条回应（OpenAI 协议要求必须一一对应，少一条就 400）。
   但**执行是串行的**，没有真正并发——多个互不依赖的调用本可以并行以降低延迟。
6. **搜索结果解析脆弱**：依赖页面结构，长期需换官方 API。
