# AgentLab · 多步工具调用 Agent

> 一个**会自己决定用什么工具、几步做完、失败后改策略**的 Agent 实验台。
> 重点不在「调通一次 function calling」，而在**能不能观测它、约束它、量化它**。

与常见的「Agent demo」的区别在于三件事：**执行轨迹可回放**、**失控防护可验证**、
**能力可量化评估**。这三件恰好是 Agent 从玩具走向可用的分水岭。

---

## 一、它做什么

给一个任务，Agent 自己规划并调用工具完成，例如：

| 任务 | 它会怎么做 |
| --- | --- |
| 「信息增益和基尼指数有什么区别？」 | 检索课程知识库 → 带章节出处作答 |
| 「本课程期末成绩怎么构成？」 | 检索课程 FAQ 与大纲 → 汇总成占比表 |
| 「用 Python 生成前 20 个斐波那契数并求和」 | 写代码 → 沙箱执行 → 报出结果 |
| 「帮我查一下 DeepSeek 最新发布的模型版本号」 | 联网搜索 → 必要时抓取页面 → 归纳 |
| 「先算 15 乘以 24，再告诉我 360 的平方根」 | 计算器 / 沙箱 → 两步给出两个结果 |

工具集（6 个）：

| 工具 | 说明 |
| --- | --- |
| `search_course_kb` | **复用 course-rag 项目的混合检索 + 重排**，返回带章节出处的原文 |
| `web_search` | 联网搜索（免 API Key，Bing/百度双引擎回退） |
| `fetch_url` | 抓取网页正文（含内网地址拦截，防 SSRF） |
| `run_python` | 沙箱执行 Python（独立进程、超时强杀、清空环境变量） |
| `calculator` | AST 白名单求值（**不用 eval**） |
| `current_time` | 当前时间（避免模型对「今天/最近」瞎猜） |

## 二、三个核心设计

### 1. 执行轨迹（Trace）：每一步都能回放

一次运行会记录：模型想了什么、调了哪个工具、传了什么参数、返回了什么、
耗时多少、烧了多少 token、是否触发防护。全部结构化落盘为 JSONL，
前端可以逐步回放——**不依赖日志文本去猜**。

```json
{
  "run_id": "c73233d410fe",
  "task": "信息增益和基尼指数有什么区别？",
  "brain": "deepseek-chat",
  "stop_reason": "finished",
  "metrics": {"num_steps": 3, "num_tool_calls": 1, "num_failed_tools": 0,
              "total_ms": 4120.5, "total_tokens": 2871, "recovered_from_failure": false},
  "steps": [
    {"index": 0, "kind": "tool_call", "content": "先查课程资料",
     "tool_call": {"name": "search_course_kb", "arguments": {"query": "信息增益 基尼指数"}}},
    {"index": 1, "kind": "tool_result", "tool_result": {"ok": true, "elapsed_ms": 1086.2}},
    {"index": 2, "kind": "final", "content": "两者的区别是…"}
  ]
}
```

### 2. 失控防护：五种机制，每一种都有测试

Agent 失控基本都源于这几处没设好，所以它们不是「顺便加一下」，而是主循环的一等公民：

| 机制 | 拦住的失控情形 |
| --- | --- |
| `max_steps` | 无限循环、越查越发散 |
| `max_seconds` | 单任务挂太久 |
| `repeat_tolerance` | 反复调用同一工具同一参数「原地打转」→ 注入提醒要求换策略 |
| `max_consecutive_failures` | 工具连续失败还在硬试 → 要求基于已有信息作答 |
| `max_observation_chars` | 一次网页抓取撑爆上下文窗口 |

每种机制都有对应的单元测试，而且是**用可编程假大脑精确构造边界场景**来测的
（例如「让模型连续 6 次调用同一个工具」），比跑一遍真实模型更能暴露防护缺陷。

### 3. 量化评估：结果层与过程层分开

```
工程层（与决策后端无关，任何模式下都成立）
  工具执行成功率 / 轨迹完整率 / 防护触发率 / 平均耗时

能力层（必须用真实模型才有意义）
  任务成功率 / 工具选择准确率 / 失败恢复率 / 平均步数 / token 成本
```

判据用三种方式组合，避免「关键词硬判」的脆弱性：
`expected_tools`（该用的工具）、`answer_must_include`（答案要点）、
`forbid_tools`（**不该用的工具**——例如课程内问题跑去联网就算失败）。

## 三、快速开始

```bash
cd agent-lab

# 复用 rag 的虚拟环境（两边核心依赖一致，省一次 torch 下载）
..\rag\.venv\Scripts\activate
pip install -r requirements.txt        # 只补 httpx / bs4 / lxml / tzdata 等

copy .env.example .env                 # 填 LLM_API_KEY 才会启用真实决策
```

### 命令行

```bash
python -m scripts.run --preflight "信息增益和基尼指数有什么区别？"   # 先看工具是否可用
python -m scripts.run "用 Python 生成前 20 个斐波那契数并求和"
python -m scripts.run --json "今天几号" > trace.json                # 导出完整轨迹

python -m scripts.traces                       # 列出历史运行
python -m scripts.traces --failed              # 只看失败的
python -m scripts.traces --show c73233d410fe   # 回放某一次
python -m scripts.evaluate                     # 跑任务评估集
```

### 网页实验台

```bash
python -m scripts.serve            # 默认 http://127.0.0.1:8010
```

左侧实时显示 Agent 每一步在做什么（流式），右侧是工具自检状态与历史运行列表，
点历史记录可**回放**当时的完整执行过程。

## 四、复用关系：这个项目不是孤立的

```
course-rag（RAG 知识库）                agent-lab（本项目）
┌──────────────────────────┐          ┌──────────────────────────┐
│ 解析 → 切分 → 向量化      │          │  Agent 主循环             │
│   ↓                      │          │    ↓                     │
│ 混合检索 + 重排           │◀─────────│  search_course_kb 工具    │
│   ↓                      │  直接复用 │    ↓                     │
│ 带引用生成                │          │  + 联网 / 沙箱 / 计算     │
└──────────────────────────┘          └──────────────────────────┘
                    ↑
              检测不到时自动降级
                    │
        ┌───────────┴────────────┐
        │ 内置迷你知识库（20 个条目）│  保证单独 clone 也能跑
        └────────────────────────┘
```

### 4.1 单独 clone 也能跑（降级设计）

**问题**：`search_course_kb` 依赖同级目录下的 course-rag 项目。
如果别人只 clone 了 agent-lab 这一个仓库，这个工具就会直接报「未找到 course-rag 项目」——
而**面试官不会为了看一个 Agent 再去 clone 第二个仓库**，第一印象就此毁掉。

**做法**：内置一份迷你课程知识（`app/tools/builtin_kb.py`，20 个主题、每个 100~200 字），
用 BM25 检索，接口与 course-rag 的检索器完全一致：

| 场景 | 行为 |
| --- | --- |
| 同级有 course-rag | 用完整的**混合检索 + 重排 + 章节级引用** |
| 同级没有 | 自动降级到内置库，**功能不中断**，并在返回内容和 `preflight` 里**明确标注**用的是兜底数据 |

降级不是静默的——工具输出会写「当前使用内置迷你知识库，未接入完整课程语料」，
`/api/health` 的工具自检也会显示 `degraded`，避免把兜底数据误当成完整讲义。

### 4.2 两个 `app` 包名冲突怎么解

**真实的坑**：两个项目都有自己的 `app` 包，若天真地把 course-rag 的根目录
插进 `sys.path` 再 `import app.xxx`，就会撞名——表现为「某些模块突然变成另一个项目的实现」，
报错位置和真实原因完全不相干。

解法见 `app/tools/course_rag_bridge.py`：

1. **懒加载**：只在真正用到该工具时才加载，不拖慢普通启动；
2. **临界区隔离**：加载期间临时改 `sys.path`，同时清掉 `app.*` 的模块缓存；
3. **立刻还原**：`finally` 里恢复 `sys.path` 与模块缓存；
4. **失败可降级**：路径不对或缺依赖时降级到内置库，同时给出可操作的中文提示。

线程安全用双检锁保证，避免并发首次调用时重复加载。

## 六、测试

```bash
python -m pytest -q      # 78 个测试，全离线
```

覆盖重点：

- **计算器安全性**：`__import__`、属性穿透、推导式、赋值、超大指数等注入尝试全部被拒；
- **沙箱行为**：超时终止、stderr 捕获、**环境变量不泄漏密钥**、临时脚本被清理；
- **防护机制**：五种防护各自单独构造场景验证（包括「防护之间互相遮蔽」这类陷阱）；
- **轨迹**：落盘-加载往返一致、指标不被重复计数、单条损坏不影响整批加载；
- **评估判据**：禁止工具、关键词未命中、未正常结束等分支；
- **API**：health / tools / run / stream（SSE 事件序列）/ traces / 404 分支。

## 七、评估结果（真实模型 · deepseek-chat）

评估集 12 条任务，覆盖课程问答、跨文档汇总、多步计算、沙箱执行、联网检索五类。
判据同时约束「该用哪些工具」「不该用哪些工具」「答案要点」，并**检测礼貌拒答**
（工具失败后模型说「未能获取依据」不能算成功）。

### 7.1 能力层（真实模型决策）

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| **任务成功率** | **100%**（12/12） | 工具使用 + 答案要点 + 非拒答综合判定 |
| 答案覆盖度 | 100% | 预期要点全部命中 |
| **工具选择准确率** | **100%** | 含「课程内问题不得联网」的克制性检查 |
| 平均步数 | 3.17 | 含思考与工具步骤 |
| 平均工具调用 | 1.58 | 偏低——模型常一次并行发出多个调用 |
| 平均耗时 | 6.0 s / 任务 | 端到端 |
| 平均 token | 5254 / 任务 | 真实成本 |
| 防护触发率 | 0% | 未出现失控情形 |
| 失败恢复率 | 0% | 本轮没有工具失败，故无从体现 |

**观察到的模型行为**（设计评估时没想到、但很有价值的发现）：

1. **模型会主动并行调用工具**。「先算 15×24，再算 √360」这个任务，
   它一轮同时发出两个 `calculator` 调用，**2 步就完成**，
   比「一轮一个工具」的串行方式少一轮往返。
   （这个行为曾直接导致一次真实故障，见第八节第 7 条。）
2. **模型知道不该跨源**。t006 问课程成绩构成，它只查课程知识库，
   没有跑去联网搜「大学成绩比例」这类通用信息。
3. **答案带章节级引用**，例如：
   > **期末总成绩构成：平时作业 20% + 实验报告 30% + 期末闭卷考试 50%**
   > （《00-课程大纲与学习指南.md》 > 课程基本信息）
4. **会主动指出歧义**。算斐波那契数列求和时，它同时给出两种起算约定的结果，
   而不是只给一个数——这恰好暴露了我评估集的期望值写错了（见 7.3）。

### 7.2 工程层（与决策后端无关）

| 指标 | 数值 |
| --- | --- |
| 工具执行成功率 | 100%（零工具异常 / 超时） |
| 轨迹完整率 | 100%（步骤序列完整、可反序列化、可回放） |
| 防护触发率 | 0%（本轮无失控情形） |

> 数据来自 `python -m scripts.evaluate --tag real-fixed`，
> 报告见 `data/eval/reports/agent-eval-*-real-fixed.md`。
>
> 无 API Key 时会自动降级为离线 mock 策略（任务成功率约 50%，
> 受固定关键词映射限制），报告里会把「工程层」与「能力层」分开并标注「本次不可用」。

### 7.3 我自己评估集的错误（值得单独说）

t009 原本标注「前 20 个斐波那契数之和」为 `17710`。模型答 `10945`，
并额外说明「若按 F₁=F₂=1 起算，前 20 项之和为 17710」。

**核对后确认：模型是对的，我的期望值错了。**
从 F₀=0、F₁=1 起算的前 20 项之和是 10945。已修正任务集，
并在任务描述里写清起算约定，避免口径歧义。

这说明两件事：一是评估集的期望值必须与口径严格对齐，否则会冤枉模型；
二是模型「主动指出歧义」的行为，反而帮我发现了标注错误。

## 八、已知局限（说清边界比声称完美更可信）

1. **沙箱不是内核级隔离**。它能防住「死循环、刷屏、误删工作目录外的文件、
   子进程环境泄漏密钥」这类常见事故，但**挡不住蓄意逃逸**
   （例如通过 ctypes 调用系统 API）。生产环境应换成容器或微虚拟机。
   代码注释里写明了这条边界，而不是含糊地说「我做了安全沙箱」。
2. **联网搜索靠解析搜索结果页 HTML**，不依赖付费 API，因此
   **页面结构变化会导致解析失效**。已做双引擎回退与「解析到 0 条」的明确报错，
   但长期稳定性不如官方 API。有 Key 时替换 provider 即可，工具接口不变。
3. **评估集只有 12 条任务**，且判据以关键词为主。要下结论应扩到几十条，
   并用人工评分或 LLM 裁判交叉验证。
4. **没有长期记忆**。当前每次运行独立，不保留跨会话的用户偏好与历史结论。
5. **规划能力依赖模型本身**。主循环是「单步决策 + 观察」的 ReAct 风格，
   没有做显式的任务分解与计划树；复杂任务上不如专门的 Planner 架构。
6. **mock 策略不是 Agent**。它只做关键词到工具的固定映射，
   存在的唯一目的是让工程链路在无密钥时可被完整验证。
7. **并行工具调用是后补的支持**。初版只处理模型返回的第一个 `tool_calls`，
   而 DeepSeek 实际会一轮返回多个——第二个调用永远没有回应，
   服务端直接返回 400 `insufficient tool messages following tool_calls message`。
   现在会执行全部调用并逐条回应，`Step` 里的调用/结果也改成列表。
   **教训**：提示词里写「每次只调一个工具」并不能约束模型的真实行为，
   代码必须按协议允许的最坏情况（一轮多个）来实现。
